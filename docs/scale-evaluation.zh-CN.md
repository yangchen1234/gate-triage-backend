# 洛杉矶港量级仿真：数据、约束与实测

本次已实际把 **119,014 条合成货物流转记录写入 PostgreSQL**，通过 HTTP API 将独立仿真时钟从 0 推进到 10,080 分钟，并复查已提交的数据库状态。它证明当前本地实现可以存储、分页查询和分批推进这批数据；不代表预测了真实洛杉矶港的作业能力，也没有对 119,014 条记录执行一次全局最优求解。

原始记录、逐次 HTTP 延迟、查询计划及固定源码位于 [`evaluation/scale-2026-10-17`](../evaluation/scale-2026-10-17/)。三策略、30 个配对种子的精细模型实验是另一项评估，见[精细仿真评估](simulation-evaluation.zh-CN.md)，不能将两项实验的收益或样本量混用。

## 1. 公开事实与合成假设

港方公布的 2025 年全年吞吐量为 **10,239,318.40 TEU**，7 月为 **1,019,837.30 TEU**；全年重进口、空进口、重出口、空出口分别为 5,316,713.30、3,793.15、1,429,260.00、3,489,551.95 TEU。[洛杉矶港官方 2025 明细](https://portoflosangeles.org/business/statistics/container-statistics/historical-teu-statistics-2025)

这里的 TEU 是按箱体尺寸折算的流量单位。全年吞吐量不能直接解释成独立箱子数量、同时在场库存，或者每天都一样的实测流量。生成器仅用这些公开数字校准合成流量总量。

| 模型 | 换算依据 | 每日合成记录 | 每日模型 TEU | 总记录 |
|---|---|---:|---:|---:|
| `la_average_day` | 全年 TEU ÷ 365，四舍五入 | 17,002 | 28,053 | 17,002 |
| `la_peak_month_day` | 7 月 TEU ÷ 31，四舍五入 | 19,938 | 32,898 | 19,938 |
| `la_seven_day` | 7 个全年平均日 | 17,002 | 28,053 | 119,014 |

“峰值月平均日”没有声称是官方实际最高单日。假设 65% 的记录为 40 英尺、35% 为 20 英尺，再用 1/2 TEU 的整数分配使每日总量精确达到目标；类别按全年 TEU 比例分配。七个码头的记录数近似平均分配，这不是它们真实的市场份额。到达时间、准备时间、服务时间、约 4% 的未满足前提条件和每码头 12 个服务槽都由明确的种子生成，均为假设。

生成器分批产出，每批最多 1,000 条用于当前入库流程；不会把整个七日队列塞进工作区 JSON。关系数据库保存全部记录、状态和事件，工作区只持有运行引用和小型活动资源状态。

## 2. 两个模型各自负责什么

精细模型包含 100 个货柜的证据、独立阻塞条件、任务依赖、共同资源、CP-SAT 计划和实际执行轨迹。它负责演示“为什么不能执行、先联系谁、获得什么证据后再安排”。

港口量级模型保存七个码头的独立合成流转记录，并按每码头最多 2,000 条候选记录计算一个时间窗口。它使用有界本地队列，不声称跨 119,014 条记录实现全局最优。两者的时钟、完成数和记录集合分开，避免重复计数。

量级模型进一步简化为两个阶段：

- 进口：`vessel_unload` 到达 → 准备等待 → `gate_out` 服务。
- 出口：`gate_in` 到达 → 准备等待 → `vessel_load` 服务。

到达阶段表示合成需求进入相关作业队列；它不等于逐吊建模的卸船作业。完成数统一称为 **synthetic movements**，其中既有进口出闸也有出口装船，不能全部称为卡车交接数、吊次或真实吞吐量。精细模型的独立船舶工作单还可演示在泊作业与未来船舶进出，但不能将其完成数再叠加到本队列。

## 3. 各类中断的作用有区别

API 把操作者确认的事件转成 `phase_incidents: [{scenario_id, started_at_min}]`，作用于当前量级运行，并保留各事件原始生效时间。解除一项事件仍须保留其他事件的限制和记录原有的未满足前提条件。

| 场景 | 本量级模型中受限的阶段 | 可以继续的例子 |
|---|---|---|
| 电池事故 / 受限道路 | 进口 `gate_out`；生效后新出口 `gate_in` | 已入场的出口装船服务 |
| 确认的起重机大风限制 | 出口 `vessel_load`；生效后新进口卸船到达 | 已在堆场的进口出闸服务 |
| 航道阻塞 | 生效后新的进口船舶到达需求 | 已到场进口出闸、已到场出口装船 |
| 地震后资产待检 | 所选码头范围的合成服务槽 | 范围外独立获准的码头工作 |
| 出口通道拥堵 | 进口出闸可用槽减半 | 其他未占用资源上的出口装船服务 |
| 数据源 / 网络中断 | 标记来源新鲜度不可知，保留已有阻塞条件 | 不因遥测离线虚构物理停工或自动放行 |

量级模型不包含每艘船的真实泊位、潮汐、航道方向、货物危险等级或真实海关许可。它不会从天气预警推断实际关闭，不会自动导航或控制设备。数据中断的细粒度 TTL、证据与许可流程由精细模型承担；本量级模型中的 `source_freshness_unknown` 只说明来源观测风险，不能当作已获得新的许可。

确认受影响的进行中服务会中断，保留审计事件，恢复后按完整合成服务时长重新开始；已完成的记录不会再次完成。未来到达不会提前占用资源。没有恢复确认的事件不会因为时间过去而自动解除。多项事件按交集限制执行。

## 4. 实际 PostgreSQL / HTTP 验证

本地环境为 macOS 客户端、Docker 中的应用和 PostgreSQL 17.11。使用 seed=17，独立工作区，全部合成数据。在这次固定构建的测量前后，源码哈希相同；测量后观察到的容器量级模型与 API 哈希也与该构建记录一致。测量过程中另有开发测试可能共享本机，因此延迟是描述性本地样本，不是负载隔离的容量证明。

**测量后的读取一致性修补：**最终开发版本随后给量级汇总、记录分页、事件分页的 PostgreSQL GET 读取加入 `begin_read_snapshot`，使用 `REPEATABLE READ`，让同一响应中的版本、运行状态、总数与列表来自一致的 MVCC 快照。量级物理模型和数据库迁移未变，但 `scale.py` 的哈希已与本次测量构建不同。因此，下面的时延仍属于修补前保留的固定构建，不能说成最终修补版本重新测得的 p50/p95。此后没有重跑完整性能实验；最终 API/UI 回归另行记录。`deployment-observations.json` 中的原始容器哈希匹配也只指当时的观察，不构成最终源码相等声明。原固定源码与清单保留不变，新增修补副本、差异和哈希位于 `post-measurement-read-isolation/` 及该 JSON 的 `post_measurement_patch`。

实际操作为：创建工作区 → 提交持久化生成任务 → 等待数据库提交 → 三种分页各请求 20 次 → 84 次每次 120 分钟推进 → 用新 SQL 连接复核。

| 结果 | 实测 |
|---|---:|
| 入库记录 / 合成 TEU | 119,014 / 196,371 |
| 观察到的入库任务完成时间 | 8.877 秒（含轮询间隔） |
| 推进后的时钟 | 10,080 分钟，即 7 天 |
| 已完成的合成流转 | 114,130 |
| 原有前提未满足 | 4,577 |
| 排队 / 进行中 | 248 / 59 |
| 持久化批次审计事件 | 85（1 次入库 + 84 次推进） |
| 未来完成时间 / 缺失完成时间 | 0 / 0 |

这些完成数由合成容量和时间决定，**不是“洛杉矶港本来就能完成多少”或“产品提升了多少”**。没有用这些数据比较任何商业产品。

每次分页最多返回 100 条，网络端到端时延如下。p50/p95 由保存的原始样本线性插值计算，没有为这些样本计算独立性置信区间。

| 请求 | 样本数 | p50 | p95 |
|---|---:|---:|---:|
| 首页 100 条 | 20 | 27.47 ms | 37.85 ms |
| 中间 offset 页 100 条 | 20 | 136.10 ms | 166.80 ms |
| Fenix 过滤页 100 条 | 20 | 21.60 ms | 24.42 ms |
| 推进 120 分钟 | 84 | 521.87 ms | 741.66 ms |

中间 offset 页明显较慢，保留了这个结果。当前实现有 offset 上限；后续可用 `(arrival_min, id)` 游标分页降低深页扫描成本，不能将首页延迟套用于所有位置。

新 SQL 连接通过 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 观察到：首页走 `ix_wb_scale_arrival` 索引；中间页仍需扫描前缀；终端候选查询有索引过滤和排序。实际计划保存在 `database-inspection.json`，它们是当前本地缓存状态下的计划，不能直接等同 HTTP 延迟。

新连接读取到了已提交的 119,014 行、完整资源状态及连续的 85 个审计序号。这证明跨请求和连接持久化；本次量级测量没有模拟进程崩溃，不能称为崩溃恢复测试。

## 5. 内存与存储口径

在开启 Python `tracemalloc`、逐行计算哈希和汇总的生成器测量中，七日数据流耗时 18.038 秒，追踪到的 Python 峰值分配约 **2.99 MiB**。这只覆盖生成器测量进程中的相关 Python 分配，既不是应用服务器峰值，也不是 PostgreSQL 内存。1,432 条输入的 120 分钟纯队列计算重复 20 次，p95 为 6.27 ms；HTTP 推进还包含查询、事务、更新、汇总和序列化，必须使用上一节的端到端数据。

测量后运行资源 JSON 为约 9.3 KiB；全部记录位于 PostgreSQL 中。在只保留这一批量级运行时，数据库报告 movement 表及其索引/TOAST 等合计约 **275.44 MiB**，其中索引约 **64.70 MiB**；批次事件关系约 **14.27 MiB**。这些关系大小包含更新产生的存储状态，不能把生成器的几 MiB 分配说成整个产品只需要几 MiB。原始字节数和统计范围保存在 SQL 检查报告。

`deployment-observations.json` 另保存一次测量后的 Docker 内存观察，它不是峰值测量，不能据此承诺生产资源配置。

## 6. 可复现运行

先按 `README-workbench.md` 启动应用和 PostgreSQL。下面的操作会创建自己的合成工作区，不覆盖团队数据。

```sh
.venv/bin/python scripts/benchmark_scale.py \
  --url http://127.0.0.1:8088 \
  --profile la_seven_day \
  --seed 17 \
  --samples 20 \
  --output evaluation/scale-local-rerun
```

输出包含入库任务 ID、运行 ID、逐次请求、时钟窗口、最终状态、生成器流哈希和源码哈希；访问令牌只在进程内存中使用，不写入产物。需要运行 SQL 检查时，先设置自己的本地 `WORKBENCH_DATABASE_URL`，再使用结果中的运行 ID：

```sh
.venv/bin/python scripts/inspect_scale_database.py \
  --run-id YOUR_RUN_ID \
  --output evaluation/scale-local-rerun/database-inspection.json
```

固定源码副本及清单位于 `source-snapshot/`、`frozen-source-manifest.json`。现有参考执行使用 15 个量级模型回归测试，覆盖流量整数校准、种子一致性、每次资源容量、96 完成数负控制、无未来预订、活动任务中断、来源离线、灾害阶段隔离、叠加限制和恢复后原有阻塞保留。数据库/API 的写入鉴权、版本冲突、幂等任务和真实 PostgreSQL 路径还有独立集成测试。
