# 实时决策与演示数据系统补充规范

版本 1.1 · 2026-10-17 · 补充主技术规范。此文的毫秒、分钟和资源配置是产品设计及演练参数，不是港口实测 SLA。

## 1 交付与运行边界

独立分支 `codex/fullstack-simulation-demo` 提供自己的 FastAPI 入口、React 网页、PostgreSQL 数据库和后台工作线程。旧版 `main.py`、团队 API 和线上 Render 服务继续使用原合同。默认只允许本地模拟；没有 Terminal49 密钥时必须显示未配置，不能以模拟成功冒充真实接入。

实时系统需要回答三个不同的问题：**刚收到什么、现在能做什么、下一步安排什么**。网页数字来自服务端工作空间快照；刷新网页不能重置数据，关闭网页不能让服务端时钟变成另一个时钟。

## 2 事件驱动决策闭环

1. 接收事件：记录事件 ID、来源、对象、发生时间、观察时间和本地接收时间。保留原始内容及摘要哈希。
2. 验证与持久化：验证工作空间能力令牌，真实 webhook 还需验证原始请求体签名。按来源事件 ID 去重。数据库提交后才向外确认收到。
3. 合并证据：按字段和来源水位判断新旧；延迟旧消息不得覆盖已观察到的新状态。重复事件不能产生第二次任务、交接或费用。
4. 评估条件：分别计算扣留、可提报告、文件、预约、现场权限、重量复核、温度和资源等条件。未知保持未知，通信恢复不能自动视作撤销扣留。
5. 形成行动：异常产生带责任角色、依据、缺失证据和下一步的并行任务。紧急度影响响应顺序，但不能绕过许可条件。
6. 重排计划：模拟模式用当前已观察到的状态重新求解；重排不能预知未来关闭或恢复。已完成作业不可倒退，正在执行的资源占用仍计入约束。
7. 原子提交：状态、修订号、任务投影、证据和审计在同一事务提交。网页通过服务端推送获知新修订，再读取完整快照。
8. 人工接手：接手、开始、等待外部处理与提交新证据是不同操作。按快照版本提交，冲突时先刷新，不能覆盖另一人的变更。

### 2.1 触发条件

| 变化 | 必须重新评估 | 不能自行推断 |
|---|---|---|
| 新增或删除 provider hold | 当前来源扣留、可提条件、后续任务 | 不能由重量或温度正常推断海关已放行 |
| 可提状态、LFD、费用更新 | 准备队列、期限与解释 | 费用优先不能成为放行授权 |
| 独立重量复核 | 重量异常及其后继任务 | 不撤销其他独立限制 |
| 冷藏新读数 | 冷藏响应任务与紧急度 | 不推断道路安全或付款完成 |
| 局部关闭、限流和恢复 | 对应资源的可用容量与候选安排 | 不关闭所有码头，不跨码头转移仍在原地的箱子 |
| 数据源离线、延迟、恢复 | 数据新鲜度、未知标记和核实待办 | 不把上次已知扣留清空 |
| 新任务状态或新到达 | 可执行任务、资源安排与队列 | 不把检查任务计作完成提柜 |

## 3 实时接口、并发与可靠性

- HTTP 读取使用工作空间令牌 `X-Workspace-Token`；修改同时带 `If-Match` 修订号与 `Idempotency-Key`。令牌保存在浏览器本地，只控制该工作空间。
- 对同一重试键先查已提交响应，再检查修订号。超时后原样重试应返回原成功结果；同键不同请求体返回冲突。
- 后台求解和实验以持久化 job 运行，记录输入修订、状态、租约、尝试次数及结果。旧修订求出的计划不得被当成当前有效计划。
- `GET /api/v1/workspaces/{id}/stream` 提供 SSE 修订通知。浏览器使用可附带令牌的 `fetch` 流；断线重连后读取当前快照，推送本身不是唯一事实存储。允许轮询降级，界面须显示连接状态。
- `POST /api/v1/workspaces/{id}/playback` 控制服务端播放、暂停和速度。工作线程推进模拟时间并提交审计；浏览器只发控制指令，不本地伪造指标。
- 不把当前本地单进程部署称为高可用集群。多副本部署前必须验证分布式播放租约、迁移锁、worker 竞争与反向代理 SSE 超时配置。

验收目标：一般读取本地交互顺畅；优化允许数秒并显示处理中。不得用未经测量的 p95 延迟或吞吐承诺代替实测结果。并发、重试、断线恢复和数据库重启后的持久性需要实际测试。

## 4 同步开发的数据模拟台

### 4.1 同一个服务端世界

每个工作空间独立保存场景、随机种子、时间、到达记录、证据、任务、资源、已完成作业和播放设置。使用 100 个合成货柜，保留 Terminal49 结构与现场模拟覆盖层的区别。业务来源层和运营覆盖层不得互相伪装。

模拟时间可暂停、逐步推进和加速。进入场景时保留来源说明及假设。选择新场景创建独立工作空间；回放跳转仅用于回放模式，不允许把正在模拟的已完成提柜回滚。

### 4.2 演示控制

| 控制 | 服务端行为 | 观众应看见 |
|---|---|---|
| Play / Pause / Speed | 持久化播放设置并由 worker 推进时间 | 共享时钟、连接状态、实际完成量随时间变化 |
| Step 5 / 15 / 60 min | 原子推进离散事件世界 | 新证据、完成任务、资源占用和队列变化 |
| East gate closed / restricted / open | 对指定车道更新容量 | 局部受影响，其他可执行工作继续 |
| Power / Customs feed | 模拟电力和 provider 通信变化 | 已知状态仍可追溯，缺失数据明确显示 |
| Delay / Duplicate / Recover | 注入迟到、重复与恢复数据 | 水位、计数和审计证明没有错误回退或重复处理 |
| Submit verification | 显式产生模拟复核证据 | 只解决关联问题；独立扣留继续存在 |

所有手工事件标为模拟。历史事故只提供背景，模拟的 30、90、120 分钟等时点不是 2024 年事故的实时时间线。

## 5 优化与利益平衡

硬约束先于目标：许可、已知扣留、任务先后、资源能力、局部容量和正在进行的作业必须满足。求解器在此范围内使用可选区间、资源互斥和累计容量，按滚动时域安排可推进的任务。

界面提供吞吐、均衡和恢复配置，用同一套约束体现偏好差异。至少展示有效完成交接、积压、平均等待、长尾等待和未完成数量。按货主或承运组观察等待分布，避免仅挑容易处理的柜子。无法完成的任务必须列出阻碍，不能从分母移除。

FIFO、紧急度和约束优化使用相同到达、信息可见范围、资源限制及按对象固定的服务时长。实验返回逐 seed 的结果与均值；持平或变差应如实呈现。等服务时长对照用于验证物理容量：两条车道、每次 5 分钟、240 分钟、100 个初始就绪柜，最多完成 96 次交接。

## 6 RAG、实时 API 与大模型各自负责什么

**RAG 检索的是解释依据，webhook 更新的是业务事实，优化器安排的是许可范围内的行动。** 三者不能互相替代。

首版本地实现可检查的来源检索：按查询从已整理的规范条目和官方来源清单返回相关片段、来源链接、适用范围及限制。无需云端 API。没有调用生成模型时界面必须称为 source retrieval / RAG-ready，不能声称大模型生成了答案。

未来启用云端 RAG 时，先检索获准文档，再让模型生成有引用的解释或交班草稿。实时快照作为明确标记的结构化上下文，不能从旧事故文档推断今天道路已关闭。模型不能撤销扣留、改写观察证据、授权出闸或直接控制资源。模型超时应退回确定性解释，关键流程继续可用。

Terminal49 webhook 的官方接口采用原始 body 的 HMAC-SHA256 签名与 `X-T49-Webhook-Signature`，notification ID 用于去重。恢复时重新读取资源做对账；不要假设所有漏掉通知都能自动补发。实际账号覆盖和限流以接入时能力探测为准。

参考：[Terminal49 webhooks](https://terminal49.com/docs/api-docs/in-depth-guides/webhooks)、[MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

## 7 登录、资源与部署

当前本地版使用 Docker PostgreSQL 的独立命名卷和 `127.0.0.1:54329`，网页服务 `127.0.0.1:8088`。不需要购买数据库或登录新的账号。默认开发凭据只用于本机；生产配置从环境变量读取。不要提交 `.env`、工作空间令牌、真实货柜数据或云端密钥。

真实 Terminal49 需要账号 API token 和 webhook secret；真实 LLM 需要服务商配置。公开部署需要服务托管、数据库连接串、HTTPS 和用户访问策略。这些不是模拟 demo 的前置依赖；本轮不修改团队线上应用。

## 8 验收清单

必须实际验证：PostgreSQL 持久化；刷新保留工作空间；两个工作空间隔离；过期修订拒绝写入；超时重试不重复执行；后台任务可查询；播放可暂停；断线重新读取当前状态；迟到与重复不误更新；撤销单个问题不撤销独立扣留；局部关闭只影响相关资源；实际完成量不等于计划数量；公平比较不保证优化必胜；界面键盘、窄屏、加载、失败和空状态可用。

开发完成记录写入 `docs/workbench-verification.md`，列出实际执行的检查、环境和已知限制。规范条目本身不代表实现已通过验收。

## 9 Port Optimizer 截图参照与交互要求

用户提供的 Port Optimizer Track & Trace 截图作为信息组织参考，不代表取得产品代码、商标使用权或与其建立集成。本应用保留自己的名称和视觉识别。

采用其适合高频运营工作的组织方式：左侧缩小对象范围，主区域显示紧凑货柜表，按状态切换，勾选对象后发起批量协调，右侧查看对象详情。截图中的船舶列表需要真实船舶字段支持；当前 fixture 缺少对应资料时，不得创造船名、船期或实有码头归属。范围筛选使用当前确有的模拟闸口、货物类型和服务组。

表格须支持明确的列排序、搜索、筛选、可见列偏好、勾选单行与当前页、批量选择数量和清空选择。已完成模拟交接与 provider 已报告历史离场分别显示，不能合并计入本次有效完成量。表头和筛选应在操作时保持可识别，窄屏允许表格横向滚动并保留详情入口。

新增 **内部协调请求**：用户选择一组货柜，指定责任角色、服务类别、标题和说明，保存到 PostgreSQL。请求可在本应用内查看、转为处理中或已解决，保留修订和审计。其状态与货柜事实、许可和物理作业相互独立。界面须明确：创建请求只保存内部工作记录，不发送给港口、海关、船公司或司机，也不创建真实预约。

API：`GET/POST /api/v1/workspaces/{id}/requests` 和 `PATCH /api/v1/workspaces/{id}/requests/{request_id}`。写入沿用令牌、修订号和幂等键。服务端检查所有货柜属于当前工作空间，限制批量大小；已知扣留不能由请求的 resolved 状态解除。

## 10 首版优化能力的可解释边界

当前 CP-SAT 使用可检查的加权目标：有效交接、紧急检查、等待年龄和规划结束时间共同影响安排。它不是已证明的分层最优或硬性最长等待保障。服务组等待分布用于显示取舍，不保证每组必定达到相同结果。运行中的作业受保护；尚未开始的计划随新证据重算，未实现固定五分钟的全计划冻结窗口。

平均与 P90 等待首先描述已完成样本，未完成对象需同时展示等待下界、积压和截尾情况。恢复时间若没有预先配置正常服务目标，则标记不可识别，不用任意猜测数字代替。结果中的 OPTIMAL 只说明当前有限模型、已观察输入和加权目标的求解状态，不能扩大为真实港口全局最优。
